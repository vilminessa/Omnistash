# Гид для ИИ-агентов: связь двух ПК через link

Пара машин для живых тестов: **vilmpc** (100.101.230.19) и **vilmnote**
(100.66.102.36) — обе в сети Tailscale, соединение прямое. Агенты не
говорят друг с другом напрямую (opencode такого канала не даёт):
каждый работает с **локальным демоном** `tools/link.py` на 127.0.0.1,
а демоны соединены между собой по Tailscale.

```
[агент на vilmpc] -> localhost:19571 -> демон link <- TCP 18571 <- демон link <- localhost:19571 <- [агент на vilmnote]
```

## Разовая подготовка (человек)

1. На обоих ПК: `git pull` (нужен только `tools/link.py` — он
   самодостаточный, stdlib, чужих зависимостей нет).
2. Придумать токен (одинаковый на обоих ПК) и дать его обоим агентам
   в промпте старта.

## Запуск демонов (по разу на ПК, в отдельном окне или агентом)

```powershell
# vilmpc (эта машина)
python tools/link.py serve --id vilmpc --token <ТОКЕН> --peer 100.66.102.36

# vilmnote
python tools/link.py serve --id vilmnote --token <ТОКЕН> --peer 100.101.230.19
```

Демон пишет в консоль свои порты и готовую команду правила брандмауэра
(Windows спросит разрешение при первом запуске).

## Промпт старта агента (шаблон)

> Ты — агент на машине **vilmpc** (id `vilmpc`). Связь с агентом на
> **vilmnote** — через канал link: токен `<ТОКЕН>`, порт управления
> 127.0.0.1:19571 (по умолчанию `--port+1000`). Стартуй с
> `python tools/link.py status` (пир онлайн?) и
> `python tools/link.py state get` (что уже сделано). Пиши свои события:
> `python tools/link.py log "..."`, состояние теста —
> `'<JSON>' | python tools/link.py state set <ключ>` (в PowerShell JSON
> только пайпом: кавычки в аргументе он съедает). Следи за чужими
> сообщениями: `python tools/link.py tail --follow`.

На vilmnote — то же с id `vilmnote`.

## CLI (одинаков на обоих ПК)

| Команда | Что делает |
|---|---|
| `status` | пир онлайн/RTT/задержка, последние заметки |
| `log "текст" [--level warn]` | строка в журнал (видна паре) |
| `state set ключ [JSON]` | своё состояние (LWW, паре видно сразу). **В PowerShell JSON передавайте пайпом**: `'{...}' \| python tools/link.py state set ключ` — PS 5.1 съедает кавычки в аргументах (JSON доедет как `{a:1}`), пайп их не портит |
| `state get [ключ] [--verbose]` | сведённое состояние обоих ПК |
| `tail [--last N] [--follow] [--json]` | журнал; `--follow` — живой поток |
| `wait [--timeout СЕК]` | **авто-пробуждение**: блокируется до первой записи ПИРА (свои не будят) и выходит с кодом 0 — запускайте в фоне хоста, уведомление о завершении процесса придёт само; таймаут = код 3 (перезапустить), нет демона = код 2 |

## Авто-ожидание почты (чтобы человек не «тыкал» агента)

Агент держит в фоне хоста (opencode: background shell):

```powershell
python tools/link.py wait --port 18571        # или --timeout 900
```

Процесс молча висит; как только пир пишет в `log` — процесс выходит с
кодом 0, печатая запись. Хост агента получает уведомление о завершении
фоновой команды — это и есть сигнал «есть почта». Дальше агент:
`tail --last 20` (что нового), отвечает через `log`/`state`, перезапускает
`wait`. Договорённости:

- будит только запись пира (свой `log` не будит — иначе петля);
- когда агенту нужен ответ, он пишет именно `log` (`state` — данные,
  будильник его не дёргает);
- после каждого ответа `wait` перезапускается (один цикл — одна почта).

## Ловушка живой LAN-пары: zapret/WinDivert и брандмауэр

Проверено на живой паре vilmpc↔vilmnote. Диагностика по шагам:

1. **Сначала брандмауэр**: без Allow-правила Windows тихо роняет SYN
   (не RST!) — картина один в один с zapret. Лечение: `netsh advfirewall
   firewall add rule name="omnistash-mesh" dir=in action=allow
   protocol=TCP localport=<порт>` (и UDP для DHT) **от администратора**.
2. **Потом winws**: `--wf-tcp`/`--wf-udp` в cmdline winws (см.
   `Get-CimInstance Win32_Process -Filter "Name='winws.exe'"`) -
   WinDivert перехватывает **только перечисленные порты**. Если наших
   портов (mesh/18571/1000) в списках нет - zapret при чём не он.
   Порядок проверки важен: в нашей паре DROP делал брандмауэр, а winws
   оказался ни при чём (порты не в wf-списке).
3. Проверять реальную доступность адреса сокетом (`connect_ex`), а не
   «ping проходит». Обход: Tailscale-адреса (100.x) или порт <1024.

## Шлюз в Docker (link-хаб + MCP) — «коннект двух агентов»

Выделенный канал пары в одном контейнере (по образцу MCP-гейтеев;
hop = MCP, как в статье про agent gateways): **link-хаб**-брокер (порт
18581) + **MCP-сервер** streamable-HTTP (порт 8809). Оба порта
публикуются **только на Tailscale-адресе** vilmpc — в LAN/WAN не
светятся. Токен один на всё (link-рукопожатие и Bearer MCP).

```powershell
# vilmpc, из корня репозитория (токен в репозиторий НЕ попадает)
$env:TOKEN='<ТОКЕН>'
docker compose -f gateway/compose.yaml up -d --build
```

Подключение агентов (бриф для обеих сторон):

```powershell
# link-демон каждого ПК набирает ХАБ (а не друг друга напрямую):
python tools/link.py serve --id <pcA|pcB> --token <ТОКЕН> --peer 100.101.230.19:18581

# MCP-инструменты (опционально; URL http://100.101.230.19:8809/mcp,
# Bearer <ТОКЕН>): channel_log, channel_read, channel_state_set,
# channel_state_get, channel_status
```

Плюсы: журнал/состояние живут в docker-томе (переживают падения),
hub связывает обоих агентов брокером, MCP даёт стандартный доступ
инструментами без CLI. Governance как в шлюзах: Bearer на каждый
запрос (401 без), allow-list = явный список инструментов, журнал
вызовов — `docker logs omnistash-hub`.

Ловушки при сборке (закрыты, чтобы не повторять): mcp 2.x — `FastMCP`
переименован в `MCPServer` (`mcp.server.mcpserver`); Starlette не
принимает `middlewares=` в конструкторе (`add_middleware`); у
`streamable_http_app()` включена защита от DNS-rebinding — нужны
`transport_security` с точными Tailscale-хостами, иначе 421 на любом
нелокальном Host; флаги `--port/--dir` в `link.py` идут **после**
подкоманды; падение MCP не должно ронять контейнер (entrypoint
держит hub и перезапускает MCP отдельно).

Порт управления = `--port+1000`; при другом `--port` добавьте `--ctrl`.

## Соглашение по ключам состояния (чтобы агенты понимали друг друга)

| Ключ | Пример значения | Смысл |
|---|---|---|
| `stage` | `"B3: прогоняю каталоги"` | что именно делает ПК сейчас |
| `test` | `{"name": "catalog_restore", "status": "running"}` | текущий тест |
| `verdict` | `{"name": "catalog_restore", "ok": true, "note": "файл 2.1 МБ"}` | итог теста |
| `env` | `{"version": "0.1.4", "mesh": true, "encrypt": false}` | версия/настройки прогона |

Договорённости: команды отдают JSON в stdout (удобно парсить), журнал —
нормальные строки; потери и перезапуски channel чинит сам (догон
`req/replay`), двойной запуск демона на одном ПК запрещён (разные
`--port`/`--dir` — можно для локальных проверок).

## Важно про доступность mesh (внешний vs LAN)

Ссылки из `state.env.mesh.addr` проверяй **сокетом, а не словами** —
UPnP может не подняться (роутер молчит на SSDP), и тогда наружу уходит
только LAN. Фактическая проверка перед network_sweep:

```python
# внешний порт: закрыт (10061), если UPnP не пробросил - не ври, проверь
python -c "import socket; s=socket.socket(); s.settimeout(8); print(s.connect_ex(('ВНЕШНИЙ_IP',38574)))"
```

- внешний `connect_ex` вернул `0` → годится и WAN, и LAN;
- вернул `10061`/таймаут → **только LAN** `192.168.x.x:38574`; сообщи
  это паре явно, иначе она уйдёт по внешнему адресу и «не найдёт».
Оба узла за одним роутером в LAN — NAT не участвует, достаточно LAN-IP.

## Автовосстановление: супервизор link_watch

Фоновые процессы умирают (смена суток, рестарт хоста) — без
супервизора канал молчит молча, а агенты «тыкают» юзера.
`tools/link_watch.py` проверяет при каждом запуске: демон отвечает на
`status`? процесс `wait` жив? — недостающее поднимает отсоединёнными
процессами (переживают выход watch) и пишет в `link_data/watch.log`:

```powershell
# один проход (задача Windows зовёт именно его)
python tools/link_watch.py once --id vilmpc --token <ТОКЕН> --peer 100.101.230.19:18581
# или циклом, если задача недоступна
python tools/link_watch.py loop  --id vilmpc --token <ТОКЕН> --peer 100.101.230.19:18581
```

Задача Windows (раз в минуту, без админа): `schtasks /Create /TN
OmnistashLinkWatch /SC MINUTE /MO 1 /F /TR ...` с командой `once` выше.
Токен в определении задачи хранится открытым текстом — та же модель
доверия, что аргументы CLI и файлы профиля. Сам `wait` дополнительно
переживает рестарт демона (автопереподключение 1 с); двойной запуск
демона на одном порту — честная ошибка (без SO_REUSEADDR).
