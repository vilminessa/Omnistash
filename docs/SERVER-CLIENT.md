# SERVER-CLIENT — раздел «Сервер» и «Клиент»

Дата: 2026-11-03. Basis: `d1ce071` (DESIGN-UI шаги 1–7 закоммичены).
Документ фиксирует архитектуру, права доступа, конвейер воспроизведения и
порядок исполнения S0–S7. Это спецификация: код в этой сессии меняется
только в порядке §9. Связанные документы: `docs/DESIGN-UI.md` (UI клиента —
те же токены и доступность), `docs/mesh-platform.md` (TLS-канал и аттестация),
`docs/ACCEPTABLE_USE.md` и `docs/LEGAL-REVIEW.md` (взрослый гейт, публичные
тексты,Third Party notices).

## 0. Термины (фиксированные; использоваться в коде и комментариях)

| Термин | Что означает в этом документе |
|---|---|
| **сервер** | Тот же процесс Omnistash, что сейчас (окно + очередь + скан), запущенный дополнительно с `--serve`: он поднимает HTTPS-слушатель рядом с окном и остаёт единственным владельцем базы, хранилищ и очереди. Серверный режим — Windows (DPAPI в `app/google_auth.py` остаётся в силе). |
| **клиент** | Браузер (или второе окно Omnistash), который не имеет доступа к базе и к папкам хранилищ: говорит с сервером по HTTPS и воспроизводит видео напрямую из байтов сервера. |
| **скоуп** | Право на токене доступа (`read`, `watch`, `queue`, `mark`, `sources`, `mesh`, `accounts`, `server_config`, `desktop`). Сервер решает скоуп, клиент только честно показывает, что ему не выдано. |
| **аттестация и пин** | Эфемерный сертификат из `app/mesh/channel.py` несёт расширение `ATTEST_OID` (SPKI, подписанное identity-ключом Ed25519); клиент запоминает отпечаток SPKI (SHA-256) по TOFU и отказывает при подмене. |
| **HLS-конвейер** | Раздача видео для браузера: `ffprobe` определяет кодек дорожки, `ffmpeg -f hls ... -c copy` пишет плейлист `index.m3u8` и сегменты `seg<N>.ts` в кеш профиля, плеер читает их по обычным HTTP-запросам. Ре-encode по умолчанию выключен. |
| **честная подпись** | «не найден», «не получен», «не выдан», «доступен только на сервере» — как есть. Ни выдуманных 0→100 %, ни серой кнопки вместо объяснения (тот же принцип, что `docs/DESIGN-UI.md` §4.4 и §5.6). |

Ограничения проекта, которые задают раздел: лицензия PolyForm Noncommercial
(нельзя GPL/AGPL-зависимости; `hls.js` — Apache-2.0 по метадате пакета
`registry.npmjs.org/hls.js` v1.7.4, проходит), ничего не скачивается в
рантайме интерфейсом (плеер лежит в `ui_src/vendor/`, грузится со своего
адреса), страница окна и страницы клиента не делают внешних запросов
(`tests/test_gui.py`, `tests/test_ui_watch.py`), TLS всегда и
порт вне зоны перехвата DPI (тот же приём, что `mesh_port`, `app/settings_schema.py:502`),
взрослый гейт решается на сервере и не обходится клиентом
(`docs/PLAN-15H.md:11-14`, `app/legal.py`), русский по умолчанию и английский
как опция (`app/i18n.py`), ffmpeg не встраивается в UI, новые `@keyframes`
запрещены кроме `pulse`/`cat-sweep` (`docs/DESIGN-UI.md` §4), переходы только
из токенов §2.7.

## 2. Разделение: кто чем владеет

**Сервер** (единственный владелец):
- база (`app/db.py`), хранилища (`app/storages.py`), очередь (`app/queue.py`),
  скан/синк (`app/indexer.py`, `app/sources.py`), mesh-участие и доверие
  (`app/mesh/*`), настройки (`app/settings_schema.py`), журнал, ffmpeg, wormhole;
- решает взрослый гейт и скоупы токена; пишет журнал аудита;
- окно — как сейчас; `--serve` поднимает слушатель в том же процессе.

**Клиент** (не имеет доступа к базе и диску):
- та же разметка `ui_src/index.html` + `app.css` + `app.js`, тот же набор
  вызовов, но через `POST /api/<имя>`;
- воспроизведение: `/watch/<video_id>` (hls.js, субтитры, список файлов);
- локальные предпочтения: тема, шрифт, язык — `localStorage`, серверный вид
  окна не меняются (§8);
- нативные цели (`pick_folder`, `open_folder`, `open_url`, `open_file`,
  `close`, `browser_*`, вход OAuth) не вызываются: вместо них поле пути +
  `storage_check` и честная подпись «доступен только на сервере».

Разделение прав — не «тонкий клиент»: клиент с полными скоупами делает всё,
что окно, кроме нативных диалогов; клиент с `read`+`watch` — только смотрит
и играет.

## 3. Транспорт

Вызов: `POST /api/<method>`, `Content-Type: application/json`,
`Authorization: Bearer <token>`, тело — массив позиционных аргументов
(`[arg]`, как их передаёт pywebview) или объект именованных аргументов
(`{"key": ...}`); пустое тело и `{}` — ноль аргументов, чтобы метод
`get_initial()` не получил лишний позиционный `None` (тот же нюанс, что
`ui_src/app.js:481-484`). Ответ — тот же Python-объект, что возвращает `Api`,
в JSON (`ensure_ascii=false`); отказ процесса (`{error: "Переиндексация уже
идёт"`) приходит подписью самого `Api` при 200, 409 остаётся байтовым маршрутам.

| Код | Что сервер говорит | Что делает клиент |
|---|---|---|
| 200 | результат метода | как в окне |
| 400 | `{error: "битый запрос: …"}` | тост с причиной, метод не повторяется вслепую |
| 401 | `{error: "ключ доступа не принят", code: "pairing"}` | одна строка-баннер «привязка не завершена», опрос не пишется каждый кадр |
| 403 | `{error: "не выдан скоуп", scope: "queue"}` | честная подпись цели: «не выдано право queue» |
| 404 | `{error: "не найдено"}` для файла/обложки | «файл не найден», не пустая картинка (§честность) |
| 409 | конфликт (идёт тот же процесс: скан/перенос/repack) | подпись «уже выполняется на сервере» |
| 413 | файл больше лимита | честный размер в подписи |
| 429 | `serve_rate_mbit` или лимит зрителей исчерпан | «лимит отдачи сервера», полоса не выдумывается |
| 500 | `{error: "<тип>: <текст>"}` | тост; журнал сервера содержит подробности |

Байтовые маршруты (GET и HEAD, тот же TLS и Range, что mesh-сервер):
- `GET /thumb/<video_id>` — обложка, `ETag` вместо data-URI (право `read`:
  она часть карточки, а не воспроизведение);
- `GET /media/<file_id>` — байты с `Range` (206 с `Content-Range`, честный
  416 на битый запрос, `Accept-Ranges`), `serve_watchers_max` — сколько
  зрителей одновременно, сверх лимита 429 с подписью (право `watch`);
- `GET /subs/<file_id>` — WebVTT: sidecar `.vtt` как есть, `.srt` конвертится
  на лету, `.ass` и другие форматы — честный 415 с именем формата (право `watch`);
- `GET /hls/<video_id>/index.m3u8` и `seg<N>.ts` — из кеша (§6); путь кеша
  строится по id строки, чужое имя и `../` — честный 404 по подписи
  (право `watch`);

Страницы и файлы клиента (S4, GET и HEAD; сама страница — не данные, право
решает токен внутри неё):
- `GET /watch/<video_id>` — страница воспроизведения с меткой сервера
  (`Cache-Control: no-store`); если `ui_src/watch.html` не в источнике, 404
  называет причину («страница воспроизведения не собрана»), не молчит;
- `GET /app.css`, `/watch.js`, `/vendor/hls.js` — файлы клиента по одной
  карте (traversal по чужому пути — 404), `ETag` по sha256 и 304; вендор
  закреплён по sha256 в `ui_src/vendor/hls.js.meta.json`.

Права ключа (S5, §4): `GET /whoami` — сервер называет скоупы предъявленного
ключа (`{paired, label, scopes}`), значений токенов в ответе нет; без ключа —
401 «привязка не завершена», `POST /whoami` — 405 (это чтение, а не вызов
метода). Клиент по этому списку подписывает недоступные цели до запроса
(«не выдан скоуп <имя>», «доступно только на сервере») и не отправляет вызов,
которому право не выдано; решают права по-прежнему сервер и тот же список.

Привязка (S6, §5): `POST /pair` — без `Authorization`, тело `[{"code": …}]`,
сервер выдаёт `{ok, token, label, scopes}`; отказ называет причину: 401 «код не
принят» / «сервер не показывал код», 429 «перебор затормозен» (`retry_in`),
`GET /pair` — 405 (значение кода читается только окном). `POST /pair` тоже
пишется в журнал — метки токена и число попыток, без значения кода.

Адресная проверка (S6, §7): когда задан allowlist, соединение с адреса вне
списка отказано до раздачи чего-либо — 403 «адрес клиента не в allowlist» и
запись в журнале; loopback всегда свой. Право на данные по-прежнему решают
скоупы на ключе, адрес их не заменяет.

Никаких чужих хостов: HTTP включается только по метке сервера
(`window.OMNISTASH_HTTP`), которую ставит `--serve` — страница окна живёт
строкой (`about:`), а превью может подаваться обычным статическим сервером и
должно оставаться на мок-бэкенде, а не становиться битым клиентом. Адрес
берётся из `base` метки или `location.origin`. Токен — `localStorage`
(`omnistash.token`), привязка — §5. `fetch` не уходит на чужой адрес; тест
страницы проверяет именно это (§9 S0).

## 4. Модель прав (скоупы)

pairing (§5) и правится в настройках сервера. Публичные методы `Api` — 125:
104 из них доступны по HTTP, 17 требуют нативного окна, 3 становятся локальными
на клиенте, 1 внутренний. Из 104 целей две выполняются только человеком в окне
сервера (`serve_pair_begin`, `serve_consent_accept`) — они подписаны отказом до
запроса и отказаны сервером второй раз (§5, §7).

## 5. TLS, привязка, порт

- TLS всегда: для клиента материал строит `app/http/tls.py` — эфемерный
  ECDSA P-256 с SAN (`localhost` + адрес привязки), TLS 1.3 минимум, PEM
  пишется во временный файл на мгновение и удаляется (ключ живёт в памяти).
  `app/mesh/channel.py:server_context()` остаётся для mesh: там ключ Ed25519 со
  SPKI-аттестацией и собеседник — не браузер. Замер на этой машине
  (in-app Chromium, loopback): сертификат Ed25519 отвергается рукопожатием
  (`ERR_SSL_VERSION_OR_CIPHER_MISMATCH`), ECDSA и RSA доходят до решения
  человека о доверии (`ERR_CERT_AUTHORITY_INVALID`).
- Сервер пишет отпечаток SPKI страницы в журнал при подъёме слушателя — человек
  видит, каким ключом слушатель работает СЕЙЧАС. Материал эфемерный и меняется
  при каждом подъёме, поэтому отпечаток — информация, а не якорь доверия;
  сравнение по отпечатку не «мы включили HTTPS», но и не защита от подмены.
- Пин сертификата в `localStorage` НЕ реализован и не должен появляться:
  эфемерный ключ менялся бы при каждом перезапуске, и клиент считал бы
  подмену на каждом плановом подъёме. Якорь доверия для браузера — одноразовый
  код привязки (§5 ниже) плюс предупреждение браузера, решение о доверии
  самоподписанного сертификата принимает человек. Для mesh-канала проверка
  своя (`channel.verify_peer`, SPKI-аттестация) — там собеседник не браузер.
- Привязка (S6): сервер показывает в окне короткий код (6 цифр или 4 слова —
  тот же рендер, что `app/mesh/sas.py`); клиент вводит его на `POST /pair` →
  сервер выдаёт токен со скоупами пресета (`serve_pair_scope`: viewer =
  read+watch, editor = +queue+mark, operator = все скоупы кроме нативного
  окна), клиент кладёт ключ в `localStorage`. Код одноразовый и живёт
  `serve_pair_minutes` минут; в памяти держится только SHA-256 кода, значение
  кода по HTTP не отдаётся (`serve_pair_begin` выполняется только окном).
  Истёкший или чужой код назван причиной отказа, а не «неверный код» молча.
- Тормоз перебора: 5 неверных кодов с одного адреса → задержка, которая растёт
  (30 с … потолок 600 с) и пишется в журнал аудита; количество токенов
  ограничено (`MAX_TOKENS`). Отозвать ключ — `serve_token_revoke` по метке-id;
  «ключа нет» назван причиной, а не тихим успехом.
- Порт вне зоны перехвата DPI: как `mesh_port` (рекомендуемая зона 444–1023,
  по умолчанию не 80/443 и не 1024–65535). `serve_port` по умолчанию 1001
  (рядом с mesh 1000).

## 6. Медиа и воспроизведение (HLS на лету)

1. Проба: `ffprobe` дорожки видео/аудио — кодек. Позиция `moov` не проверяется:
   HLS — новая перекладка в MPEG-TS, faststart для неё не нужен.
2. Если кодек отдаётся без ре-encode (H.264 + AAC; без аудио — тоже copy) →
   `ffmpeg -f hls -hls_time 4 -hls_playlist_type vod -c copy` в
   `profile/hls_cache/<video_id>/`: ffmpeg пишет media-playlist `index.m3u8`
   и сегменты `seg<N>.ts` (не `master.m3u8` — мы не сочиняем свой формат).
   Кеш переиспользуется по сигнатуре файла (`size|mtime|sha256` в `meta.json`)
   и сбрасывается хуками окна при repack, migrate, rebind и удалении строки;
   второй плеер того же видео ждёт перекладку (замок на видео), а не строит
   её параллельно.
3. Если кодек не годится для браузера (HEVC/VP9/AV1) → честный отказ:
   «кодек <имя> — браузер не воспроизводит без ре-encode», и опция
   `serve_hls_transcode` (по умолчанию выключена: CPU и качество); без
   энкодера в сборке ffmpeg отказ называет энкодер, без ffmpeg или ffprobe —
   «инструмент не установлен» / «кодек не прочитан».
4. Аудио (.mp3/.m4a/.opus) — прямо через `/media` с `Range`, HLS не нужен.
5. Субтитры: sidecar `.vtt` отдаётся как есть, `.srt` конвертится в VTT на
   лету; извлечение встроенных дорожек (`ffmpeg -f webvtt`) — вне шага S3:
   чужой формат назван 415 по имени, отсутствие названо «субтитры не
   найдены» (не пустой трек).
6. Ограничения отдачи: `serve_rate_mbit` (тот же `pacing.RateLimiter`),
   `serve_watchers_max` — сколько зрителей одновременно, одним лимитом на
   всё: раздача `/media` держит слот до конца раздачи, `/hls` занимает
   сессию плеера (видео + адрес, TTL активности) — сегменты не плодят
   зрителей, отказ по кодексу или инструменту слот не занимает. Сверх
   лимита — 429 с честной подписью.
7. `hls.js` (Apache-2.0 по метадате пакета, v1.7.4 закреплён в
   `ui_src/vendor/hls.js.meta.json` по sha256) грузится со своего адреса
   `/vendor/hls.js` на страницу `/watch/<video_id>`: рантайм ничего не
   скачивает из сети. Пункт в
   `THIRD_PARTY_NOTICES.md` и `docs/LEGAL-REVIEW.md`.

## 7. Экспозиция (как сервер выходит наружу)

`serve_enabled` — по умолчанию выключен. Режимы `serve_bind` решает
`app/http/bind.py` и называет причину отказа:

- `loopback` (по умолчанию) — `127.0.0.1`, только этот компьютер;
- `lan` — адрес сетевого интерфейса машины; требует явного согласия человека
  (`serve_expose_consent`); интерфейса нет — отказ «адрес сети не найден»,
  слушатель остаётся на loopback;
- `tailscale` — адрес из диапазона CGNAT `100.64.0.0/10` (ZeroTier вне плана:
  адрес из интерфейса не различим, и серверный режим — Windows); согласия те
  же, интерфейс не поднялся — отказ назван;
- `wildcard` (`0.0.0.0`) — «обычный порт»: требует согласия И непустого
  allowlist адресов/CIDR (`serve_allowlist`); без списка слушатель НЕ поднимается
  (`ServeError` с причиной), битый элемент списка — тоже отказ, а не «половина
  списка понята».

Согласие принимает только человек на сервере: `serve_consent_accept` выполняется
окном и отказана по HTTP (`http.expose_consent`), прямая запись
`serve_expose_consent` в `save_setting` тоже отказана с той же причиной — иначе
клиент с `server_config` открыл бы доступ наружу сам себе. Карточка не рисует
флажок (поле скрыто), решение — диалог «Что уходит наружу» в виджете
`_serve_access`.

Диалог согласия перечисляет, что уходит: подписи строк, обложки, длительности,
размеры, счётчики состояния (`poll`), байты медиа по запросу. Пути диска не
уходят: `/media` отвечает по `file_id`, не путём. Предупреждение DPI: порт в
зоне перехвата 1024–65535 и 80/443 — риск замедления/искажения трафика, тот же
текст, что `settings_schema` для `mesh_port`; выключать DPI-утилиту не нужно.

Адресная проверка: при заданном allowlist соединение с адреса вне списка
отказано до раздачи страницы и байтов — 403 «адрес клиента не в allowlist» и
запись в журнале; loopback всегда свой. Для `lan`/`tailscale` список
необязателен: открыта сеть того, кто достает порт, а право решают скоупы.

Журнал аудита: `profile/serve_audit.log` — метка ключа → метод → код результата
→ адрес; хвост обрезает `rotate_log_file`. Журнал не содержит токенов, кодов
привязки и путей дисков. Журнал программы (`omnistash.log`) видит режим
экспозиции, отпечаток эфемерного ключа и причину отказа (согласия нет, адрес не
найден, allowlist битый).

## 8. UI клиента (что отличается от окна)

- та же разметка и те же токены DESIGN-UI; никаких новых `@keyframes`;
- тема/шрифт/язык — локальные (`localStorage`), подписи приходят из того же
  словаря `app/i18n.py` через `ui_texts` с `request.language` (это чтение
  подписей, а не смена настройки: окно сервера остаётся на своём языке); смена
  языка клиента пересказывает строку прав и подписи отказов новым словарём, а
  не оставляет текст прежнего языка;
- вместо системного диалога папки — поле пути и `storage_check` (доступность
  проверяет сервер); пустое поле названо причиной, а не «тихий отказ»;
- права ключа читает `GET /whoami`: строка «права ключа: … · не выдано: …»,
  а на недоступной цели — подпись «не выдан скоуп <имя>» текстом (не серой
  кнопкой, не молчанием); нативные цели — «доступно только на сервере»;
  запрос, которому право не выдано, клиент не отправляет;
- `/watch/<video_id>` — доступность и узкий экран по §7 DESIGN-UI; переход
  в плеер требует права `watch` и отказывает подписью до перехода;
- виджет доступа по HTTPS (`_serve_access`, тип `serve`): состояние слушателя
  («поднят»/«не поднят», адрес, режим, согласие, allowlist, число ключей,
  активен ли код, сколько было неверных попыток) читается `serve_state` по
  праву `server_config`; непрочитанное состояние названо «не прочитано», а не
  пустым списком;
- согласие «что уходит наружу» — диалог в окне сервера (`serve_consent_accept`
  + галка и предупреждение про зону перехвата DPI); выбор режима наружу в окне
  спрашивает этот диалог ДО сохранения, отказ возвращает select на прежнее
  значение. Клиент цель подписывает текстом «принимает человек на сервере» и
  не отправляет вызов; в карточке поля `serve_bind` на клиенте лежит та же
  подпись;
- привязка: в окне — кнопка «Показать код привязки» (`serve_pair_begin`,
  значение кода отдаёт только окно), на клиенте — поле кода и «Привязать этот
  браузер» (`POST /pair`, без ключа). Поле лежит вне карточки настроек
  (`#pair-box` → `pair-code-out`): карточка читается целью `get_initial`,
  которой без ключа не выдано, и иначе клиенту негде было бы ввести код —
  молчание вместо входа. Блок виден ровно пока привязка не завершена (ключа
  нет, ключ отозван или не принят); после удачной привязки он прячется, а
  карточка перечитывается (`loadInitial`) и права читаются заново
  (`GET /whoami`); 429 называет задержку (`retry_in`), список ключей показывает
  метки и скоупы и даёт «отозвать» (`serve_token_revoke`);
- заодно закрываем открытые пункты DESIGN-UI: №5 (табовая семантика строки
  вкладок — `tablist`/`tab`/`tabpanel`, `aria-selected`, `aria-controls`,
  roving tabindex, стрелки ←→ с Home/End) и №25 (активная вкладка: цвет +
  underline + фон, и текстовый «Где я» на узком экране), и M13 (`queue_retry`
  с `attempt_chain=True` — флаг «Попробовать другую дорогу» рядом с кнопкой
  повтора, итог называет, какая дорога прогоняется).

## 10. Риски и «не делаем»

| Риск / решение | Как отражается в коде |
|---|---|
| Самоподписанный эфемерный сертификат: браузер показывает предупреждение | Материал ECDSA с SAN (Ed25519 браузер отвергает рукопожатием — замер на этой машине); отпечаток SPKI пишется в журнал при подъёме слушателя — человек видит, каким ключом слушатель работает сейчас. Пин отпечатка в `localStorage` НЕ реализован (материал меняется при каждом подъёме, и клиент считал бы подмену на каждом плановом перезапуске); якорь доверия — одноразовый код привязки плюс предупреждение браузера, решение о доверии принимает человек. Текст объяснения честный, без «мы включили HTTPS, значит всё безопасно» |
| Чужой `fetch` как источник supply chain | Только `location.origin`; `hls.js` лежит в репозитории, рантайм не скачивает |
| Запись из HTTP-потоков в sqlite при живущей очереди | Пишущие операции идут тем же потоком, что в окне (`Api`-воркеры), читающие — свои соединения; тест на loopback с идущим сканом |
| Ре-encode HEVC/VP9/AV1 жрёт CPU и качество | По умолчанию выключен (`serve_hls_transcode`), отказ с подписью кодека |
| Открытый порт + DPI-перехват | Зона порта вне 1024–65535 и 80/443, предупреждение в подписи `serve_port` |
| Перебор кода привязки | Тормоз после 5 ошибок, лимит токенов, запись в аудит |

Не делаем в этом разделе: Linux/NAS-сервер (DPAPI остаётся, вне плана),
обход блокировок через клиент, публичная экспозиция без явного согласия,
ре-encode по умолчанию, второй владелец базы, `desktop`-цели по HTTP,
выдуманные индикаторы прогресса.
