# DESIGN-UI — спецификация интерфейса Omnistash

Дата: 2026-10-31. Basis: `2ce35b8` + волны 1–3 из `docs/PLAN-15H.md`.
Файл описывает дизайн (токены, планировку, «веяния», доступность) и план внедрения.
Это документация: код в этой сессии не менялся, изменяться будут только
`ui_src/app.css`, `ui_src/index.html`, `ui_src/app.js` в порядке из §8.

## 0. Термины (фиксированные, использоваться в тексте и в комментариях кода)

| Термин | Что означает в этом документе |
|---|---|
| **токен-система** | Единый слой именованных значений (`--bg`, `--surface`, `--line`, `--text`, `--accent`, … плюс новые токены цвета, отступов, радиуса, elevation, типографики, длительностей и easing). Все правила в `app.css` читают токены, а не литералы. |
| **веяния** | Слой анимаций и микровзаимодействий: отклик на hover/press/focus/выбор/появление панелей и диалогов. Только `transform`/`opacity`/цвет, только CSS, только из токенов длительности и easing (§4). |
| **виртуальное окно прокрутки** | Модель библиотеки: в DOM живёт только видимая часть строк/плиток плюс overscan, страницы по 120 подтягиваются по мере прокрутки (`app.js:22`, `app.js:2363-2421`). Высота строки/ряда — общий токент и инвариант с JS (§3.1, §8 шаг 2). |
| **боковая навигация против вкладок** | Выбор: левая панель (`nav`) или строка вкладок. Критерий — число равноправных секций и тип перехода (§3.9, §6). |
| **честный прогресс** | Детерминированная полоса только когда итог известен; иначе недетерминированная полоса + счётчик. Никаких выдуманных 0→100 % и «почти готово» (§4.4). |

Ограничения проекта, которые задают дизайн: лицензия PolyForm Noncommercial
(нельзя тянуть GPL/AGPL-зависимости), CSS-only анимации без новых библиотек,
страница вшивается в окно строкой и не делает внешних запросов
(`tests/test_gui.py:375-386`), публичные тексты о взрослой площадке нейтральны
(`docs/PLAN-15H.md:104-105`), русский по умолчанию, английский как опция
(`app/i18n.py`), ffmpeg не встраивается в UI.

## 2. Токен-система

### 2.1 Принципы

1. Два слоя: **примитивы** (`--gray-…`, не используются в правилах) и
   **семантика** (`--bg`, `--surface`, `--text`, …). В правилах — только семантика.
2. Существующие имена сохраняются и расшивляются: `--bg`, `--surface`,
   `--surface-2`, `--widget`, `--line`, `--text`, `--muted`, `--accent`,
   `--accent-2`, `--warn`, `--ok`, `--err`, `--info`, `--radius`, `--shadow`,
   `--row-h` остаются; добавляются `--line-strong`, `--focus`, `--on-accent`,
   `--ok-*/--err-*/--info-*` для границ статусов, `--focus-ring`, `--log-bg`,
   `--log-text`.
3. Тема переключается одним блоком `[data-theme="light"]`
 (`ui_src/app.css:36-50`); внутри темы значения только литералы, никаких
   `rgba()`-правил в компонентах (замена #10 и #24 из §1).
4. Внешних шрифтов нет и не будет (`tests/test_gui.py:375-386`): системный
   стек остаётся (`ui_src/app.css:64`), плюс моно-стек для чисел журнала.
5. Имена токенов — в духе DTCG (Design Tokens Community Group): `color`,
   `space`, `size`, `radius`, `shadow`, `type`, `motion`. Это рамка для
   структуризации, не зависимость.

- Plex «Using the Library View» + Jellyfin docs: действия над видимыми/выбранными

## 4. Анимации и микровзаимодействия («веяния»)

### 4.1 Общие правила

- Анимации только CSS (`transition`, `@keyframes`), без библиотек;
  `@import` и внешние запросы запрещены (`tests/test_gui.py:375-386`).
- Анимировать `transform`, `opacity`, цвет/границу; не анимировать
  `height`/`width`/`grid-template` — кроме детерминированной полосы прогресса,
  где `width` читает реальный процент (это не «веяние», а данные).
- Длительность и easing только из токенов §2.7; никаких литералов в правилах
  (сейчас `.scan-fill { transition: width .2s }` — `app.css:423`).
- 60 FPS: трансформации без layout-reflow; hover-эффекты не меняют
  `box-shadow` у строк в виртуальном окне прокрутки (стоимость на 120+ строк).
- Каждое состояние имеет переход, и переход асимметричен: вход
  `--ease-expressive`, уход `--ease-exit` — Carbon различает productive и
  expressive и отдельно exit-easing.

### 4.2 Микровзаимодействия по компонентам

### 4.3 `prefers-reduced-motion` (блок целиком)

```css
@media (prefers-reduced-motion: reduce) {
  /* Все «веяния» выключаются; смысл состояний остаётся через цвет,
     underline, подпись и dot — не через движение. */
  *, *::before, *::after {
    transition-duration: 0.01ms !important;
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
  }
  .scan-fill.indet { animation: none; background: var(--widget); } /* уже есть: app.css:973-976 */
  .notice, .toast, .overlay-card { transform: none; }
  .tile:hover, .row:hover { border-color: var(--line-strong); }    /* hover без движения */
  .btn:active { transform: none; }
}
```

Обоснование: MDN `prefers-reduced-motion` (`reduce`/`no-preference`) и
WCAG SC 2.3.3 (Animation from Interactions) — анимация не обязательна и
должна быть убираемой; web.dev motion guidance: не двигаться на 5+ секунд,
анимация не должна быть единственным носителем смысла. Существующий блок
(`app.css:973-976`) расширяется до глобального — и остаётся CSS-only.

### 4.4 Честный прогресс

1. Детерминированная полоса — только когда итог известен (`total > 0`):
   процент = фактическое значение, полоса заполняется 0→100 % и не убывает
   (Carbon Progress bar, NN/g progress indicators).
2. Недетерминированная — когда итог неизвестен: sweep-полоса + счётчик
   («получено 214 карточек», «получено 3.2 MB, итог неизвестен»).
   Carbon: indeterminate convey «обработка идёт», без ложных цифр.
3. Никогда не «почти готово», не фиктивные 99 %, не «загрузка…» при пустом
   результате: пустое значение подписывается «не получено» / «неизвестно»
   (реализовано в `app.js:4444-4474`).
4. Отказ оставляет уже полученное и говорит, что не получено
   (`app.js:4586-4611`) — UI не «сбрасывает» прогресс визуально.
5. Полоса имеет имя и значение для AT: `role="progressbar"`,
   `aria-valuenow/min/max`, `aria-label`; indeterminate — без `aria-valuenow`.
6. Статусы полосы: active / success / error (Carbon) — цвет dot + текст
   подписи (`--ok`/`--err`/`--info`), не только цвет.
7. Skeleton-заглушки используются только там, где структура известна заранее
   (карточки каталога до получения обложек); при неизвестной структуре —
   indeterminate + счётчик, не skeleton (skeleton обещает контент, которого
   может не быть: NN/g skeleton-vs-spinner, LogRocket, Mejtoft).

## 6. Три варианта планировки

### Вариант A — «плотная таблица + боковая навигация»

```
nav 264px (Библиотека · Источники · Очередь · Коллекции · Площадки · Настройки)
content: toolbar (поиск/фильтры/вид/колонки) → chips → notice → scan
         sticky header → виртуальное окно прокрутки → meta → sel-bar (sticky)
foot: счётчики · журнал (collapse)
```
Плюсы: 6 равноправных секций как secondary navigation (Carbon порог «больше
пяти»), действия над библиотекой уходят в боковую панель (Plex), список
остаётся максимальным по плотности (120 строк в окне, tMM/Carbon data table),
каталог остаётся карточным внутри своей секции.
Минусы: боковая панель съедает 264 px при узком экране (media 900 px → 180 px,
уже есть `app.css:998-1000`); табы-площадки становятся пунктами nav, и adult
gate должен быть виден в nav (§3.10).

### Вариант B — «вкладки + карточный каталог с токенами»

```
tabs (Библиотека · Источники · Очередь · Коллекции · Площадки · Настройки)
content: toolbar → chips → scan → сетка карточек (minmax(--tile-min)) +
         «плотный список» как secondary view внутри Библиотеки
sub-nav внутри Настроек и Площадок (табы/сегмент)
```
Плюсы: максимум ширины для контента (нет nav), табы соответствуют текущему
коду (`index.html:26-32`) и NN/g (один ряд, 1–2 слова); карточки хорошо
читаются на широком экране; каталог уже карточный (`app.css:980-996`).
Минусы: 6 вкладок + динамические площадки легко превышают один ряд и
«1–2 слова» (NN/g), при 120 px подписях вкладок с числами появляется cap;
скан/добавление библиотеки остаются в toolbar, что противоречит Plex/Jellyfin;
плотность списка ниже (карточки вместо строк).

### Вариант C — «рабочая панель + строка выделения»

```
nav 264px + content; правая панель деталей 320px (открывается Enter на строке)
sticky selection bar над content; workspace-контекст: коллекция + фильтры + выбор
журнал как collapsible bottom
```
Плюсы: details без модального диалога (меньше фокус-ловушек), batch-опации
всегда на виду, progressive disclosure для редких полей; соответствует
Carbon «expandable rows = progressive disclosure».
Минусы: правая панель конкурирует с виртуальным окном прокрутки по ширине
(при 12 колонках горизонтальный скролл уже есть, `app.js:2236-2264`);
виртуализация + live-панель = больше state-синхронизации в `app.js`;
на узком экране панель превращается в диалог (возврат к A/B).

### Рекомендация

**A как основа**, B сохраняется как режим просмотра каталога и как
fallback на широком экране (<1200 px — A с nav, >1400 px — B без nav, один
ряд вкладок), C внедряется только как «строка выделения» (уже существующий
`sel-bar`) и как non-modal панель деталей на экране ≥1300 px.

Почему:
1. Secondary navigation из 6 равноправных секций — Carbon UI shell left
   panel (>5 пунктов → левая панель; три уровня вложенности не поддерживаются,
   значит Библиотека/Каталог внутри площадки остаются табами страницы).
2. NN/g: табы только для равноправных разделов, один ряд, 1–2 слова;
   динамические площадки + «18+» ломают это правило.
3. Plex/Jellyfin: действия над видимыми/выбранными объектами в верхней
   панели списка, библиотековые действия (скан, добавить) в боковой панели —
   A делает это разделение естественным.
4. tinyMediaManager/Carbon: настраиваемые колонки и toolbar настроек таблицы
   — плотная таблица остаётся главным инструментом библиотеки (100k записей
   листаются как 100, `app.js:4-6`).
5. Виртуальное окно прокрутки: строки плотнее карточек, overscan и `PAGE=120`
   работают лучше с фиксированной `--row-h`; C добавляет второй живой слой,
   который не даёт выигрыша при том же объёме данных.

   (`docs/PLAN-15H.md:104-105`); правки хинтов колонок
   (`app/settings_schema.py:175-177`) только убирают имя, не меняют смысл.
3. **Честные отказы по `kind`**: тексты отказов бэкенда (`app.js:4586-4611`,
   `app.js:320-327`) остаются как есть; UI не «美化» отказ и не заменяет его
   нейтральной фразой, если бэкенд сказал причину.
4. **Не выдуманные подписи и состояния**: пустое значение — «не получено»,
   «неизвестно», «недоступно на площадке»; нет фиктивных процентов, нет
   fake loading (см. §4.4, `app.js:4444-4474`).
5. **Лимиты и границы запросов**: `PAGE = 120` (`app.js:22`), `POLL_MS = 500`
   (`app.js:23`), `THUMB_CACHE_MAX = 400`/`THUMB_BATCH = 100`
   (`app.js:20-21`), лимиты бэкенда на выборки — UI не подтягивает «всё сразу».
6. **Mesh-подсказки и обход/PO-токены**: подсказки о mesh остаются
   текстом настроек (progressive disclosure их только скрывает до первого
   отказа), поведение обхода не переопределяется UI; Zapret/DPI не трогается
   (`docs/PLAN-15H.md:24-25`).

   бэкенда (`statusLabel`, `app.js:320-327`) — новые имена статусов не
   изобретаются, порядок «от увидели к скачали» сохраняется; фильтр статуса
   остаётся.
8. **Гварды тестов**: `[hidden] { display: none !important; }` и отсутствие
   точечных `[hidden]`-правил (`tests/test_ui_hidden.py:25-45`),
   `#grid-rows.tiles { display: grid }` (`tests/test_grid_view.py:169-176`),
   отсутствие внешних запросов на странице (`tests/test_gui.py:375-386`).
   Токены и правила не создают новых `[hidden]`-исключений и не заводят
   `<link>`/`@import`/шрифты.
9. **Механика виртуального окна прокрутки**: overscan и синхронизация
   скролла шапки/тела (`app.js:2363-2421`, `app.js:5043`), пересчёт колонок

    «▶ Открыть в плеере» остаётся внешним вызовом (§3.2).
11. **Существующие честные тексты empty-state** (`index.html:204-205`,
    `index.html:233-234`, `index.html:280`) — правятся placement и семантика,
    смысл остаётся.
